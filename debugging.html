CHAPTER 04 LEARN BY BUILDING

把問題縮小，
讓證據帶路。

從重現、觀察到驗證，建立能應用在 Logging Service 的除錯方法。

入門 → 實作約 25 分鐘閱讀查核於 2026.11.08
本篇學習方式先讀概念，再跑教學範例，最後用練習檢查理解。範例採 C11／host 環境；平台規則與公司的內部介面需另行確認。
01 / EVIDENCE BEFORE EXPLANATION

先把「壞掉了」變成可驗證的描述。

「工具沒看到 log」是現象，還不是根因。先記錄預期與實際行為、重現步驟、時間範圍、build／decoder 版本、filter 設定，以及發生頻率。每次只改一個主要變因，保留原始輸入，才能比較結果。

觀察

產生計數增加 100，但收集端只收到 80 筆。這是可以檢查的證據。

假設

Consumer 太慢導致 buffer 滿。這需要 queue 使用量、drop counter 或可控速率實驗驗證。

不要從「加了 sleep 就好了」直接推論根因；sleep 可能只是改變時序。同樣地，增加 log 也可能改變執行時間，使 race 或即時性問題暫時消失。

本篇的分析案例是教學設計。方法可用於工作，但不宣稱這就是你團隊系統的實際 counter、錯誤碼或排查順序。
02 / LOCATE THE BOUNDARY

沿著管線，把問題縮小一段。

現象優先蒐集的證據可做的驗證
完全沒有 log執行路徑、編譯開關、runtime filter、啟停狀態使用已知會發生的單一測試事件
負載高時缺 logqueue high-water mark、入列失敗、drop counter、輸出速率固定格式，逐步提高產生速率
文字或欄位亂碼原始 bytes、格式版本、dictionary、長度與 offset拿同一筆 bytes 對照正確版本的離線 decoder
重啟附近缺資料boot/session ID、flush 行為、檔案尾端是否截斷區分正常關機與異常斷電情境
偶發 crash堆疊、輸入、ownership、編譯版本與 symbols最小化重現，使用 host sanitizer 或平台工具
AP / Modem 時序對不上clock 單位、時間基準、wrap、offset 與 drift用可辨識的共同事件校對時間關係

若計數單位不同，不能直接相減。例如 producer 計「事件」，transport 計「封包」，file sink 計「bytes」；必須先對齊語意與統計區間。

03 / SMALL TOOLKIT

用四種工具回答不同的問題。

COMPILER

Warnings

先看第一個 warning 的型別與資料流，不盲目 cast 掉它。範例用 -Wall、-Wextra、-Wpedantic。

MEMORY

ASan / UBSan

ASan 尋找部分越界與生命週期錯誤；UBSan 檢查部分未定義行為。它們不能證明程式沒有錯，也不是 data race 檢查的替代品。[A] [U]

EXECUTION

LLDB / GDB

用 breakpoint、backtrace、變數與記憶體檢視，找出錯誤發生前的狀態。Optimized build 可能使逐步執行與變數顯示不直覺。[D]

DATA

Hex dump

確認檔案裡到底有哪些 bytes。畫面解碼錯誤與原始資料錯誤是不同問題。

hexdump -C build/sample.bin
lldb ./build/log_lab
# 以下在 LLDB 提示符內執行：
breakpoint set --name parse_record
run decode build/sample.bin
frame variable n
bt
next
continue

若要穩定練習 breakpoint，可用 -g -O0 重新編譯 debug binary。Debugger 是否能啟動 target 仍受 host 權限與安全設定影響；production firmware 使用的平台 debugger 另行確認。

04 / REPRODUCIBLE EXPERIMENTS

四個實驗，練習從證據走到結論。

使用 log_lab.c 和 test_lab.py。所有輸入都是自造資料；完整建置方式見 Binary Logging 實作。

./build/log_lab generate build/sample.bin
./build/log_lab decode build/sample.bin
python3 examples/test_lab.py build/log_lab

  1. 基準：正常資料

    應產生兩筆 record，value 分別為 4660 與 1；程式回傳 0。先建立一份可信的輸入與輸出。

  2. 資料截斷

    測試腳本建立每個非空的截斷前綴。Decoder 必須失敗且回報 truncated，不能越界或把半筆資料當成完整事件。

  3. 版本與 schema 不相容

    把版本改成 2，或把 event 1 的 payload 改成一個 byte。預期 invalid。未知 event 99 則保留 hex，符合格式定義的相容策略。

  4. 緩衝區滿載

    執行 ring 子命令：容量四筆，先產生六筆，預期兩筆被丟棄。這是策略測試，不是實際硬體吞吐量量測。

想自己製造截斷檔案？
python3 -c 'from pathlib import Path; p=Path("build/sample.bin"); Path("build/truncated.bin").write_bytes(p.read_bytes()[:-1])'
./build/log_lab decode build/truncated.bin

第一筆仍可輸出，接著在檔案結尾回報 truncated。整個命令應回傳非零。已印出部分資料不代表整個檔案有效。

測試通過究竟代表什麼？

表示這組輸入與執行環境符合預期。測試涵蓋短 header／payload、邊界長度、格式錯誤、未知 ID、串接多筆與 sequence wrap；沒有證明任意輸入安全，也沒有驗證 RTOS、DMA、並行、壓縮或真實設備效能。

05 / WRITE A USEFUL FINDING

案例：log 少了，怎麼寫分析？

假設每筆大小固定，單一 producer、無 filter，使用 drop-newest queue。測量區間開始時 queue 為空；結束時已停止 producer，並完全排空 queue。

計數結果解讀
produced1000嘗試產生的事件
enqueue_ok920成功進入 queue
drop_full80因滿載未入列
dequeued / written920 / 920本案例中後段沒有額外流失

可支持的結論：在上述假設與計數定義下，80 筆事件在入列邊界被丟棄。這還不能證明 consumer 慢的原因；後續仍需檢查排程、sink 延遲與 producer burst。

下一步實驗：固定 payload 與輸出目標，只降低 producer 速率。若 drop 減少且 high-water mark 下降，就支持容量／吞吐量相關假設；再逐項排查 consumer 的時間花費。

若結束時 queue 尚有資料，需加入 pending；若採 drop-oldest，已入列的資料也可能被覆寫。守恆式必須依實際策略定義，不能照抄。

06 / COMMON FALSE CONCLUSIONS

避免這些看似合理的捷徑。

「多加幾倍 buffer 就解決了。」

可能只是延後滿載。先區分短暫 burst 與長期 producer 大於 consumer；再量測記憶體成本、等待時間與丟棄策略。

「Sequence 不連續，表示 transport 掉包。」

還可能是 filter、不同 channel、重啟或計數 wrap。必須知道 sequence 的配置點與作用域才能定位。

「ASan 沒報錯，所以可以移到 firmware。」

Host sanitizer 不覆蓋所有邏輯錯誤或目標硬體問題；alignment、ABI、排程、cache、ISR、DMA 與平台 API 都要另驗證。

「檔案已寫入，所以斷電後一定還在。」

stdio buffer、作業系統 page cache 與裝置持久化是不同層次。fwrite 成功不等於持久化；本練習只檢查寫入與 close 的結果，沒有做 crash-durability 保證。[F]

「所有錯誤都重試就好。」

重試可能重複資料、改變順序或造成無限迴圈。先依錯誤分類與操作是否可安全重複，定義上限、退避與可觀察性。

07 / READY FOR A SMALL TASK

用這張清單準備你的第一個修改。

  • 我能畫出一筆 log 的產生、傳輸與解碼路徑。
  • 我能說明這次修改的 ownership 與失敗行為。
  • 我保留了可重現的輸入、版本與預期結果。
  • 我驗證正常情況，也驗證至少一個邊界或錯誤情況。
  • 我能分開描述「觀察到的現象」「根因假設」與「已驗證結論」。
  • 我知道 host 範例與公司平台之間還有哪些差異。
建議的問題紀錄格式環境與版本 → 重現步驟 → 預期／實際 → 原始證據 → 假設 → 實驗 → 結論與限制。公司專案資料留在核准的內部環境。

完成這四篇後，可依手上的任務補充 RTOS、host daemon、協定事件或工具解碼；不必同時鑽研所有 Modem 子系統。
