CHAPTER 04 LEARN BY BUILDING

進階理解搶占、優先權反轉、ISR 交接與反應時間分析，再用 trace 檢查真機行為。

入門 → 實作約 25 分鐘閱讀查核於 2026.11.21
本篇學習方式先讀概念，再做練習檢查理解。實作環境與適用範圍見各篇說明；公司平台與內部介面需另行確認。
01 / SCHEDULE WHAT IS READY

Ready 不等於已開始執行。

接續嵌入式系統的 ISR、DMA 與 task 入門。假設一個單核心系統：RX ISR 記錄事件，RX task 擷取資料，控制 task 產生結果，背景 logger 才負責輸出。對每個 job 分開記錄 release（本次工作可開始）、first run 和 finish。等 CPU、等鎖與真正使用 CPU 是三回事；如果工作在 release 前還卡在 DMA 或中斷遮罩，端到端期限也要算上那段時間。

FreeRTOS 啟用搶占時，單核心 scheduler 選最高優先權的可執行 task；同優先權是否按 tick 輪轉，看 configUSE_TIME_SLICING。高優先權 task 若在空迴圈等待事件，仍可能讓低優先權 task 沒機會跑；用可阻塞的等待介面，並定義 timeout 行為。[F]

固定週期工作可從上一個預定喚醒點加週期（FreeRTOS xTaskDelayUntil()），而非每次做完再相對延遲。即使按時變成 Ready，也可能晚一點才取得 CPU。pdFALSE 表示這次沒有延遲，不等同應用層判定 deadline miss；另用事件時間戳判斷，並決定過期工作要補跑、略過還是進入降級模式。[D]

不要照搬 priority 數字。FreeRTOS task 的數字越大，優先權越高；Cortex-M NVIC 的數字越小，中斷優先級越高；Zephyr thread 的數字越小，優先權越高，負值是 cooperative 優先權。Zephyr 3.7.0 的 CONFIG_SCHED_DEADLINE 只在靜態優先權相同時比較 deadline，不會把整個 scheduler 變成全域 EDF。[F] [I] [Z]
02 / RESOURCE CONTENTION

低優先權的持鎖者，可以卡住高優先權工作。

  1. 低優先權 L 拿到共享裝置的鎖；高優先權 H 隨後需要同一把鎖，因此阻塞。
  2. 若沒有 priority inheritance，中優先權 M 可以搶占 L。M 雖然從未碰那把鎖，仍延長 H 的等待。
  3. 支援 priority inheritance 的 mutex 可暫時提升 L 的有效優先權，幫它早些釋放鎖。H 仍得等 L 完成必要的持鎖工作。

FreeRTOS 使用簡化的 priority inheritance；同一 task 持有多把 mutex 時，可能在釋放全部 mutex 前仍保留已繼承的優先權。不要假設解開其中一把就會立即降回原優先權。Binary semaphore 沒有 mutex 的 ownership 和繼承語意，也不能代替 mutex 解決反轉。[M]

先縮短 critical section，把可移出的 I/O 和等待拿掉；必須拿多把鎖時，建立全域 lock order。繼承無法消除 deadlock，不能讓已被 I/O 阻塞的持鎖者立即執行，也不會自動給出可拿去做時序分析的 blocking 上界。

03 / ISR TO THREAD HANDOFF

先定義事件能不能合併，再選通知方式。

需求可用的方式一定要定義的邊界
通知一個 task 有工作待清FreeRTOS direct-to-task notification。[F]設 bit 會合併重複事件；若要知道發生幾次，就用計數語意並處理上限，不把 notification 當 payload FIFO。
保留個別事件與時間戳有容量上限的 queue，放小型 descriptor。滿載時怎麼處置？若採 drop-newest，要增加丟棄計數並處理未成功移交的 buffer；成功時只移交 API 契約承諾的內容。
保護 task 間的共享裝置有 ownership 的 mutex。哪個 task 釋放、最長持鎖多久、timeout 後怎麼恢復；ISR 不拿 mutex。
把非緊急工作移出 ISRDedicated worker，或 Zephyr workqueue。[W]同一 work item 尚在排隊時再次提交不會多排一筆；同一 workqueue 中，慢 handler 會推遲後面的工作。

FreeRTOS Cortex-M 的 ISR 範例：先依周邊手冊取樣與處理中斷來源，再以 xQueueSendFromISR() 非阻塞入列，檢查成功或 queue full。pxHigherPriorityTaskWoken 使用呼叫端先設為 pdFALSE 的旗標；若變成 pdTRUE，依 port 規則在離開 ISR 前請求切換。只有落在該 port 允許範圍的 IRQ 才能呼叫 kernel API；對使用 BASEPRI 的 Cortex-M port，特別檢查 configMAX_SYSCALL_INTERRUPT_PRIORITY、NVIC priority grouping，以及 CMSIS 和寄存器使用的 priority 編碼。[I] [Q]

決定 queue 傳的是值還是 pointer。若成功入列就轉移 DMA buffer ownership，producer 不再重用；若入列失敗，ownership 沒有改變。Consumer 要在讀取結束後歸還 buffer，不能只靠 volatile 或通知送出來推論 DMA 資料已安全可讀。複習生命週期。

04 / RESPONSE-TIME ANALYSIS

用最壞反應時間檢查 deadline。

本例限定單核心、固定優先權且可搶占、沒有 release jitter、沒有額外自我暫停，且每個 task 的相對期限 D 不大於最小到達間隔 T。假設已有保守的執行時間上界 C 與資源阻塞上界 B。以下模型不計額外 ISR、context switch、cache 或 DMA 影響；不要套用到 SMP、尚未建模的等待或任意期限。[R]

令 R 初值為 Ci + Bi，反覆更新。每個較高優先權的 task j 在長度 R 的窗內可占用 CPU 多次：

R_next = C[i] + B[i] + sum(ceil(R / T[j]) * C[j] for j in higher_priority)

若收斂且 R ≤ D，模型支持這個 task 能滿足期限；若迭代值先超過期限，就無法用這些參數證明滿足期限。若 C、B 是保守上界，超過不必然代表實際會逾期。CPU 平均使用率或一次量到的最快時間，不能取代這個檢查。

05 / REPRODUCIBLE LAB

不用板子：算出控制 task 的阻塞預算。

時間一律用 µs；控制 task 的確切 blocking 上界先視為輸入，由更低優先權的共享資源工作造成。這個練習只回答控制 task 的期限是否有保證，不替整套系統定案。

Task優先權C（µs）T（µs）D（µs）
RX高3001,0001,000
控制低於 RX6502,5001,800

用 Python 3 從 repo 根目錄執行，或下載 rtos_response_time.py。不需要 Zephyr SDK 或 FreeRTOS：

python3 examples/rtos_response_time.py 0
python3 examples/rtos_response_time.py 300
python3 examples/rtos_response_time.py 600
為什麼加上 300 µs 阻塞，反應時間卻增加 600 µs？

B = 0 時收斂於 950 µs；B = 300 時迭代為 950 → 1,250 → 1,550 µs，再收斂。窗長跨過 1,000 µs，就要多容納一個 RX job；增加的是 300 µs 阻塞加 300 µs 搶占。

阻塞上界最多可以是多少？

把 B 改為 550，會收斂於 1,800 µs，恰好達到期限；551 就超過。B = 600 時，第一次超過期限的迭代值為 1,850 µs。超過後程式停止更新，不把尚未收斂的數字標成完成時間。

06 / TRACE THE TARGET

用 trace 拆出等待、阻塞與執行。

  • 對齊事件：用同一個單調時鐘記錄 ISR 進出、事件入列、task Ready／切入／切出、鎖等待／釋放與工作完成。帶上序號、task ID 和 queue 溢位計數；多核心另記 core ID，確認各核心時基是否能直接比較。
  • 找等待原因：Ready 到首次切入長，查當時執行的 task 與 ISR；blocked on lock 長，查 owner、鎖持有時間與搶占；queue 高水位和丟棄數上升，再比對 burst 和 consumer 是否被 I/O 拖慢。Trace 本身若丟事件，標記資料缺口，不從缺段定根因。
  • 同看 RAM：根據目標負載檢查 task stack、queue 容量與 pool 餘量。上游 FreeRTOS 的 stack high-water mark 是測到的歷史最少剩餘 stack 空間（以 stack words 計），不是已用 bytes；未跑到的最深 call path 仍未驗證。[S]

Zephyr 3.7.0 的 tracing 指南示範從 kernel hooks 選格式與傳輸。先用低成本的事件記錄重現高負載，並估計 instrumentation overhead；真機觀測到的最大值仍不等於已證明的 WCET。[T] 下一章封包與資料結構先分清紀錄與傳輸邊界，再練習用佇列交接資料。
