01 / NAME THE BOUNDARY

先問「封包」是哪一層的資料。

讀 logging service 時，同樣叫 packet 的東西可能是記憶體物件、已編碼的 log record，或真正的網路封包。先查函式在哪一層、收什麼、傳給誰；不要從變數名稱猜格式。

你看到什麼它的邊界由誰定義？
C struct 或 descriptor程式內的欄位、型別與生命週期。指標可指向 buffer，但指標值不是 buffer 的內容。
Log record／應用層訊息編碼器與解碼器約定的欄位、長度、byte order 與版本。它不必剛好裝進一個網路封包。
TCP segment／UDP datagram傳輸層。TCP segment 是承載 byte stream 的傳輸單位；UDP datagram 是 UDP 的訊息單位。
IP packet／鏈路 frameIP packet 有網路層地址；在 Ethernet 上，IP packet（或其片段）再放入鏈路 frame。
I/O chunk一次 read() 或 callback 交給程式的 bytes，由 I/O 介面契約決定。它不是另一層協定。

外層的 payload 可以包含內層的 header。假設用一個 UDP datagram 運送 18 bytes 的 LG v1 record：UDP payload 是整筆 18 bytes，UDP Length 是 8 + 18 = 26 bytes（不含 IP header）；LG v1 裡的 payload_length 卻只有 2 bytes。哪個長度正確，要先知道它屬於哪一層。[B] [U]

02 / STREAM VS MESSAGE

TCP 保留位元組順序，不保留應用訊息邊界。

  • Byte stream：TCP 提供可靠、有序的 byte stream。一個 send() 不對應一個接收端 recv()；兩筆 record 可能一起讀到，一筆也可能跨多次讀取。檔案或串列介面若以 byte stream 供讀取，也要自己找 record 邊界，但可靠性不一定跟 TCP 相同。[T]
  • Datagram：UDP 保留到達的 datagram 邊界，但不保證送達、順序或不重複。接收 buffer 不夠時要依 socket API 判斷截斷；不能拿下一個 datagram 補前一個。每個 datagram 裝一筆、多筆，或由應用自己拆分，仍是格式設計。

Framing 是定義 record 從哪裡開始、在哪裡結束。固定長度好切但不適合所有 payload；分隔符（例如換行）需要規定 payload 內同一符號怎麼處理；長度前綴支援變長資料，但要明確寫下長度的單位、是否含 header、最大值與 byte order。[B]

Parser 的三種結果不能混在一起。收到完整且有效的 record，就消費該筆、保留剩餘資料；格式有效但尚未收齊，就等待更多 bytes；確定格式不合法則回報錯誤。對有限資料來源，要是 EOF 時還差 bytes，這是截斷，不是繼續等待。後續要停止或重新同步，必須看協定是否定義了做法。
03 / READ BYTES BY OFFSET

看欄位契約，不靠 sizeof 猜線上格式。

Hex 每兩個字元是一個 byte；offset 從 0 計。下列是 repo 的合成 LG v1 資料，換行只是標出 16-byte header 與 payload，不是資料內容：

4c 47 01 02 02 00 01 00 01 00 00 00 e8 03 00 00
34 12

看 LG v1 欄位表：offset 4 的 02 00 是 little-endian payload_length = 2。因此整筆占 18 bytes。Offset 16 的 34 12 是 payload；按這筆 event 的 schema 解成 0x1234，也就是 4660。UDP header 的多 byte 欄位是 network byte order（big-endian）；這不會改變 UDP payload 裡 LG v1 自己的 byte order。

讀欄位前確認實際已收到的長度；收到完整 header 後才使用它宣告的長度，並先檢查格式的上限。C struct 可能有 padding、alignment 與不同 ABI，不能單靠 sizeof(struct) 或把 buffer cast 成指標來讀取 wire format。複習 C 與記憶體：bytes 與 struct。

兩筆 record 是 18 與 17 bytes，三次讀到 7、20、8 bytes，何時能解完？

第 1 次只有 7 bytes，連 header 都不夠。第 2 次累積 27 bytes，解完第一筆後保留 9 bytes。第 3 次加上 8 bytes，第二筆共 17 bytes，剛好消費完。這三次是 I/O 切塊，不是網路封包或 record 的邊界。

04 / PICK BY OPERATION

Queue 是使用規則，ring buffer 是實作方式。

資料結構不只是在宣告欄位：要看最常做的操作、可用記憶體、資料大小與最慢路徑。例如 FIFO queue 要求「先進先出」；可以用環形陣列，也可以用 linked list。兩者讓呼叫端看到相同順序，實作成本卻不同。[O] [Q]

結構何時用在 logger要付的成本
Array連續收 bytes；ID 連續且範圍小時，用索引查 event 資訊。依索引存取 O(1)；中間插入若需保持順序，通常要搬元素。要分清已用長度與總容量。
固定容量 ring按順序暫存待消費的 log 或 descriptor，不搬動剩餘元素。固定大小 item 的索引操作 O(1)；資料複製仍取決於 item 大小。容量滿時要有策略。
Linked list節點本來就在 pool 中，且手上已有要插入的位置，可用連結管理待處理項目。已有前置節點時，單向串列的插入可 O(1)；定位第 n 個要走訪。每節點要付出 pointer 空間，並管理節點生命週期。
Hash table由稀疏的 event ID 找 schema 或名稱。良好雜湊與受控負載下，查詢通常期望 O(1)，但碰撞會增加工作。固定的小字典不一定需要 hash table。

大 O 描述操作成本如何隨資料量成長，不是最壞延遲保證。特別要分開看搜尋、複製、記憶體配置與等鎖。若 queue 存的是 {data, len} descriptor，入列複製的是指標與長度，不會順便複製 payload；規定成功和失敗時由誰保有、歸還 buffer。複習 ownership。

05 / CHECK RING INVARIANTS

陣列上的位置，不等於 FIFO 順序。

本 repo 的四格單執行緒 ring：head 是下次寫的位置，tail 是下次讀的位置，count 是佇列內的 item 數。每次成功操作才推進對應的索引，走到陣列尾端就回到 0。從 tail 往前走 count 格，才是 FIFO 順序；不要從 slot 0 開始讀。專案若用相反的 head/tail 命名，以它自己的讀寫行為為準。

count == 0 代表空，count == 4 代表滿；兩種情況都可能見到 head == tail。若採用 Linux 文件示範的留一格方案，四格陣列只能裝三筆，滿空公式也不同，不可混用。這裡教的是固定大小的槽位；若 ring 存的是變長 record 的原始 bytes，一筆還可能跨陣列末端，拆成兩段。[R]

回到 service：先寫下容量的單位。容量可能是 4 筆 descriptor、4 KiB 資料、或最多 4 個尚未歸還的 pool buffer，不能互換。滿載時查採用丟新、丟舊還是阻塞，並找出 drop 計數在哪裡更新。單執行緒 ring 不等於可在 ISR 或多核心直接共享的 queue。
06 / FOLLOW ONE RECORD

不用硬體，跑完 bytes 與 queue 兩個練習。

  1. 分辨「缺資料」與「格式錯誤」。開啟 互動 Hex Decoder，解正常範例，再按「載入截斷範例」；前者應顯示 4660，後者應顯示 NEED_MORE。接著還原並把 offset 4～5 的 02 00 改為 00 02，再解碼。
  2. 看滿載、回繞與讀出順序。開啟 四格互動 queue，重設後連續按五次「產生一筆」，再消費一筆、產生一筆。先猜第 6 筆放在哪格，再依序把佇列清空。
  3. 用同一套問題讀工作程式。在核准的環境選一個事件，記下編碼函式如何定義 record 長度、接收端在哪裡檢查和消費，以及 enqueue 成功或失敗後誰負責 buffer。不把內部封包、trace 或程式碼放進本 repo。
Byte order 改反，為什麼不是 NEED_MORE？

00 02 按 little-endian 是 512，已超過 LG v1 的 32-byte 上限；即使現在只有兩個 payload bytes，也應直接回報 INVALID，而不是繼續等待。

第 6 筆寫到 slot 0，會先讀到它嗎？

不會。第 5 筆滿載被丟棄；第 1 筆出列後，第 6 筆寫回 slot 0，但 tail 指向 slot 1。後續出列依序為 2、3、4、6。slot 編號不是時間順序。

如果手上的輸出確實走 IP 網路，延伸練習是用 Wireshark 開啟公開或獲准的 capture：先展開 IP 與 TCP／UDP 欄位，在 Packet Details 選一個欄位，對照 Packet Bytes 高亮的位置。沒有對應 dissector 時，工具不一定知道你的 log record 格式。[W]
