01 / SYSTEM MODEL

先分清楚晶片、板子和 firmware。

嵌入式系統把運算放進有特定用途的裝置。寫 firmware 不只要讓輸出正確，還要知道它何時送達、可用多少 RAM、失敗後如何恢復。這一章用 Cortex-M 微控制器教觀念，不代表任何 Modem 的實際架構。[UT]

你在看哪一層？例子與文件
CPU coreCortex-M 描述核心與例外模型；用 Arm 文件查核心功能，例如中斷控制器 NVIC。
MCU / SoC晶片整合 CPU、記憶體或周邊。用該型號的原廠手冊查 memory map、clock、UART 與 DMA；同屬 Cortex-M 不代表暫存器相同。
Board用開發板的 schematic 查 LED、電源及接頭實際接到哪一根 pin；核心手冊不會告訴你。
Firmware啟動碼和 driver 把晶片與板子設定好，應用程式才有可用的 timer、輸入與輸出。板級支援套件（BSP）可提供部分啟動與周邊設定。

讀手冊的順序：核心行為查 Arm，暫存器查晶片原廠，接線查板級文件。[ARM] [TI]

02 / BOOT & MEMORY

程式在進入 main 前就開始工作了。

典型的 Cortex-M 開機流程：從 vector table 取得初始 stack pointer 與 reset handler，執行啟動碼和 C runtime 初始化，才進入 main。開機可能先經過 boot ROM 或 bootloader；實際初始化順序應看該平台的 startup code。[START]

常見 section典型 MCU 放法對除錯有什麼用？
.text / .rodata程式碼與唯讀資料通常留在 Flash。Flash 不夠時，先分辨體積來自程式碼還是常數。
.data執行時放在 RAM；初值通常隨映像檔放在 Flash，啟動時複製到 RAM。有初值的全域 buffer 可能同時消耗 Flash 與 RAM。
.bss執行時占 RAM，典型啟動流程將該區清零。映像檔小，不表示執行時的 RAM 用量小。

Linker script 決定配置；map file 用來檢查實際位址與大小。別只加總上表：stack、heap、RTOS task stacks 與 DMA buffers 也可能占用 RAM。先用前一章的資料生命週期判斷誰能讀寫，再用 map file 查資料放在哪裡。

03 / PERIPHERALS & MMIO

讀寫暫存器，可能直接改變硬體狀態。

Memory-mapped I/O（MMIO）把周邊暫存器映射到 CPU 可存取的位址。先看原廠手冊的 register width、reset value 和存取型態。例如有些旗標是 write-one-to-clear（W1C）：寫入 1 才清除指定 bit；用一般 reg |= mask 做 read-modify-write，可能把其他已是 1 的旗標也清掉。使用平台的暫存器定義與存取介面；volatile 並不能取代同步或平台要求的順序控制。[ARM] [TI]

周邊用途第一次接線／除錯先確認
GPIO按鈕輸入、LED 輸出或切換到替代功能。Pin mux、方向、pull-up/down、有效電位。
Timer週期取樣、時間戳、量測脈波。Clock source、prescaler、計數器寬度與回繞。
UART非同步串列通訊，例如 debug console。兩端 baud rate、資料位元、parity、stop bits 與訊號電位。
I²C / SPI常用於 MCU 與板上感測器通訊。I²C 查位址、pull-up 與 ACK；SPI 查 chip select、clock mode 與 bit order。[I²C]
04 / EXECUTION CONTEXT

Polling、ISR 與 DMA 不是三種互斥的架構。

  • Polling：程式定期讀狀態。若主迴圈常被其他工作卡住，實際檢查間隔會變長；短暫且未鎖存的訊號可能被漏掉。
  • Interrupt / ISR：硬體事件觸發中斷，CPU 在允許時進入 interrupt service routine。依手冊處理中斷來源、記錄必要資訊，再把可延後的工作交給主迴圈或 task。等待時間不只取決於 ISR 長度，也受遮罩、優先權與其他中斷影響。[UT] [ARM]
  • DMA：受 CPU 設定後，由 DMA 控制器搬移資料，可再用中斷通知完成。若 driver 未複製資料，buffer 在 DMA 完成前不可失效，也不能被不當讀寫或重用；有 cache 的平台還要依 driver 契約處理一致性。[TI]

Bare metal 可用主迴圈加 ISR；RTOS 可讓多個 task 各自等待事件，由 scheduler 在 ready tasks 中依規則挑選要執行的 task。以 FreeRTOS 為例，ISR 若要傳 queue，應使用適用的 FromISR API 並遵守該 port 的中斷優先權限制，不能在 ISR 阻塞等待。Queue 若存的是 pointer，入列只會複製 pointer 值，不會延長 payload 的生命週期。[RTOS]

即時不等於跑得快。若要求事件發生後 2 ms 內一定處理完，就要說明可接受的最大延遲與適用負載；平均 0.3 ms 或改用 RTOS 都不能證明滿足期限。
05 / TRACE A DEADLINE

不用板子：找出哪一筆事件逾期。

假設一個 timer 每 10 ms 觸發取樣。要求是從 timer 事件到 task 完成處理最多 2 ms，UART 將 log 送給主機則不算在內。下表時間都來自同一個單調計數器，且這段期間沒有回繞。

序號Timer 事件（µs）進入 ISR（µs）Task 完成（µs）
110,00010,05010,600
220,00020,08022,300
330,00030,65031,500
哪一筆逾期？中斷進入最慢的是同一筆嗎？

第 2 筆端到端延遲為 2,300 µs，超過 2,000 µs；另外兩筆分別為 600 和 1,500 µs。ISR 進入延遲最長的是第 3 筆（650 µs），不是第 2 筆。不要用單一階段的最大值認定整條路徑的瓶頸。

如何分辨是 ISR 太久、task 在等，還是 task 一直被搶占？

先加「完成入列」與「task 取出」的同來源時間戳，分出入列前、入列到取出、取出到完成三段。要再區分 task 實際執行時間與被搶占的時間，用 scheduler trace 查 context switch。量測本身也有成本，避免在 ISR 同步印長字串。

主機收到 log 的時間能代替哪一欄？

不能直接代替任何一欄。主機時間還混入排隊、傳輸和主機排程，也可能與裝置使用不同時鐘。追溯事件時應保留裝置端時間戳與序號；另外記錄 queue 滿載時的丟棄計數。

這是合成資料，不是在驗證真實硬體最壞延遲。接著用 RTOS 進階的反應時間分析，分別估算阻塞與搶占對期限的影響。

06 / FIRST RTOS BUILD

延伸實作：在 Linux 跑 Zephyr。

不需要開發板。依 Zephyr 3.7.0 官方環境指南準備 Linux 工具鏈、west 與 workspace；初始化 workspace 時在指南的 west init 指令加上 --mr v3.7.0 選定版本。進到 Zephyr 原始碼目錄，於 x86-64 Linux 執行：

west build -b native_sim/native/64 -d build-native-sim samples/hello_world
./build-native-sim/zephyr/zephyr.exe

成功時 console 會出現 Hello World! 和目標名稱；即使檔名是 .exe，它仍是 Linux 執行檔。Kernel 進入 idle 後用 Ctrl+C 停止。這個 target 用來驗證建置與軟體行為，不模擬指定 MCU，也不能用來證明真實中斷延遲、UART 電氣特性或 DMA 正確性。[Z]
