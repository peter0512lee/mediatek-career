01 / PRODUCER TO CONSUMER

一筆 log，是一段需要交接的資料。

把 logger 想成有限容量的資料管線：事件產生後，先決定是否收錄，再編碼、入列、傳輸、儲存與解碼。每個階段都可能失敗，因此每個交接都需要狀態與明確的資料所有權。

Event→Filter→Encode→Queue→Sink→Decode

Zephyr 是公開參考案例：frontend 負責即時過濾與入列，backend 處理輸出；deferred logging 把部分工作延後進行。它降低呼叫端的工作量，卻仍需要處理 queue 容量、資料生命週期與輸出速率。[Z]

本章所有 bytes 都是自訂教學資料。格式名為 LG v1，與 ICD、MDM、MTF、DHL 或任何廠商 modem trace 都不相容。
02 / DEFINE THE WIRE CONTRACT

先寫格式契約，再寫 parser。

LG v1 使用 8-bit byte。多 byte 整數皆為 unsigned little-endian。Header 固定 16 bytes，payload 最多 32 bytes；一筆 record 最長 48 bytes。

Offset大小欄位本教材定義
02magic固定 ASCII LG，即 4c 47
21version固定 1；其他版本拒絕
31level0 error、1 warning、2 info、3 debug
42payload_length0～32，不含 header
62event_id1 measurement、2 state；其餘顯示 raw hex
84sequence每筆遞增；32-bit 取模
124timestamp_ms本次啟動後的毫秒數；32-bit 取模
16可變payloadevent 1：u16 數值；event 2：u8 狀態 0 或 1

這些 level、ID 與欄位是本教材的選擇，不是通用標準。範例 generator 寫入固定的時間值以便重現，沒有真的讀取裝置 clock。

LG v1 沒有 checksum、壓縮、加密或重新同步設計。Magic 與長度檢查不能偵測所有 payload 損壞；production protocol 需要依可靠性需求另行設計。

04 / CHUNKS ARE NOT RECORDS

一次 read，不一定是一筆 log。

在 byte stream 上，header 可能分兩次到達，也可能一次拿到數筆 record。Parser 的輸入完整性與 I/O 的分塊方式是兩件事。POSIX read 也可能成功回傳少於要求的 bytes；具體 EOF 與錯誤處理應依介面契約實作。[IO]

  1. 累積到完整 header

    不足 16 bytes 回傳 NEED_MORE，不讀取尚未到達的欄位。

  2. 驗證格式與長度上限

    檢查 magic、version、level 與 payload 長度；不依收到的任意長度無限制配置記憶體。

  3. 等待 payload 並驗證 schema

    資料夠長後才檢查 event 對應長度與欄位值。

  4. 消費資料並保留剩餘 bytes

    一般 stream parser 回報 consumed length；剩餘資料繼續解析。範例每次向 parser 加一個 byte，所以完成時恰好一筆。

範例 parser 回傳的 payload pointer 借用接收 buffer；decoder 必須在重用 buffer 前完成讀取。本例遇到格式錯誤立即停止；檔案結束仍有半筆資料則回報 truncated，不靜默略過。

05 / FINITE CAPACITY

Buffer 只能吸收短暫落差。

若 producer 長期平均速率高於 consumer，任何有限 buffer 最終都會滿。擴大容量可以緩衝 burst，卻不能根治持續的吞吐量不足。以固定速率的簡化模型，淨累積速率是 producer − consumer；這不包含排程、封包 overhead 或 burst 的影響。

Ring 的兩種常見表示

只用 head/tail 的設計常保留一格以區分滿與空；本範例另存 count，所以四格皆可使用。不能混用兩套判斷公式。Linux circular buffer 文件示範的是特定併發與容量假設。[Q]

明確選擇滿載策略

Drop newest 保留舊事件；drop oldest 保留最新事件；blocking 把壓力傳回 producer。選擇會影響診斷能力與即時性，沒有適用所有情境的答案。

四格 queue · drop newest

依序入列 1～6，前四筆留下，5、6 被丟棄。消費一筆後再入列，可觀察位置環繞。

這是單執行緒的狀態模型。多 producer、ISR、DMA 或多核心場景還需要處理同步、cache coherency 與平台 memory ordering。此處不提供可直接移植的 lock-free 實作。
06 / VERSION & TIME

解碼正確，還需要正確的上下文。

Dictionary-based logging 用較精簡的參考值替代部分文字，再由解碼端還原。Zephyr 的 dictionary 與產生它的 build 對應；不能把它當成所有版本通用的資料表。其他系統的相容規則必須查自己的格式契約。[Z]

  • 格式版本：header 和 payload 如何解讀？遇到未知版本是否拒絕？
  • Build / dictionary ID：能否確認 trace 與 decoder 資料的對應關係？
  • 時間基準：是 wall clock、boot-relative，還是硬體 tick？頻率與單位是什麼？
  • 重啟與 wrap：32-bit 毫秒計數約 49.7 天會 wrap；重啟也可能回到零。
  • 跨來源對時：AP、Modem、PC 的 clock 可能有 offset 與 drift，不能直接把數字相同當成同一時刻。

Sequence 缺口只能提供線索：必須先知道它在 filter 前還是後遞增、是否分 channel、是否重啟／wrap，才可推論是否丟失。LG v1 的範例只展示欄位，沒有自動推論跨重啟的遺失率。

07 / RUN THE LAB

產生、解析，再故意破壞。

完整程式：log_lab.c。在 repo 根目錄執行：

mkdir -p build
clang -std=c11 -Wall -Wextra -Wpedantic -g -O1 \
  -fsanitize=address,undefined -fno-omit-frame-pointer \
  examples/log_lab.c -o build/log_lab
./build/log_lab generate build/sample.bin
./build/log_lab decode build/sample.bin
./build/log_lab ring
./build/log_lab self-test

Decoder 預期印出兩筆事件：seq=1、time_ms=1000、MEASUREMENT value=4660；seq=2、time_ms=1010、STATE value=1。Ring 範例預期 queued=4、dropped=2，然後依序消費 1～4。

為什麼 C 程式每次只 fread 7 bytes？

故意讓 header 與 payload 跨越讀取邊界，證明 parser 不依賴一次 read 恰好一筆。實際 transport chunk 大小不必是 7。

未知 event ID 應直接丟棄嗎？

這個教學格式選擇輸出 raw hex，保留診斷線索；但未知格式版本直接拒絕。其他系統要依前向相容契約決定。

把 payload 的 34 改成 35，會被偵測為損壞嗎？

不會。它仍是合法 u16 值 4661。LG v1 沒有完整性檢查，這正是格式驗證與資料完整性驗證的差別。
